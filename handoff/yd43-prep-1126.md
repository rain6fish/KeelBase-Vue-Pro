## 1. Goal and caliber

**Goal.** On a pinned, already-delivered product build, the real business users of one real delivery project each complete the same five business-goal tasks without any developer hint, and the AI path is measured against that project's existing manual process on median total time and median error count.

**Caliber — self-use delivery.** KeelBase is not a product sold to a market; it is the platform we use to take on enterprise delivery work. The test object is therefore the real business user of **one actual delivery project**, not a random third party, not a developer reproducing a recipe, not a trained re-tester. The original review proposed 3–5 people; the self-use caliber narrows this to **however many real business users that project actually has**, recorded honestly, never padded.

**Division of labour with existing rows.** `YD-28` measures a non-author developer reproducing a delivery from a recipe. `YD-36` M7 measures whether one reader can understand the pages. YD-43 measures whether a real business user can **finish the work** on real business data, with an efficiency comparison. None of the three substitutes for another.

## 2. YD-43 versus N5

N5 was the first session on the same source line: a named non-developer (an office clerk) ran an **acceptance task** on seed data and read the audit face. YD-43 moves one notch further.

| Dimension | N5 (run 2026-11-25) | YD-43 (pending) |
|---|---|---|
| Subject | A named non-developer reader, unrelated to the project's business | A real business user of the delivery project, already doing this work day to day |
| Task source | Acceptance tasks built from the audit verification scenario (object #1 / follow-up #1, read six questions, export, second entry) | The project's real business tasks, one business goal per card, no steps, real objects |
| Data | Seed data in an isolated stack (`n5rd`, objects #1) | Real business data, or a production copy |
| Pass rule | N5's five criteria (six-question grid, named second approver, `/audit/verify`, second entry, zero help) | All 5 tasks run; ≥ 4/5 independently completed; zero developer hints; plus the control comparison |
| Control group | None | Same five tasks through the existing manual process; median time and median error count |
| Reverse proof | None | Disable the AI path and run the manual group |
| Machine evidence | CSV + recording + `/audit/verify` | Task-list file + result table + audit/trace rows sharing one `conversationId` or trace id, all three matching |
| Evidence ceiling | E3; no E4; three items missing (screenshots, signed sheet, zero-help record) | E3 by default; E4 only on client-side independent attestation and a user ruling |

**The three differences that matter most:** the subject is a business user rather than a reader; the task is real work rather than an acceptance script; and YD-43 adds a **comparison against the existing manual process**, which N5 never had.

## 3. Candidate user profile

**Counts:**
- A person in that delivery project who does this batch of business day to day — business operator, finance, HR, project assistant, and similar.
- Logs in with a **real business role account** of that project, not `admin` or a superuser.
- Gives informed consent to recording and to the data being used.

**Does not count (each exclusion recorded in the record sheet):**
- The developer or the implementer of the feature.
- Test, implementation, or our own delivery staff.
- An AI agent, browser automation, or any simulated operator.
- A re-tester who has been trained on the flow — training is a hint.
- A random third party with no business relation to the project.
- Anyone using demo data, or a project where only our own staff use the system.

**N.** Use the actual number of available business users. Fewer than three: record N as it is. N = 0: the item is judged **not achieved**; it must not be written as achieved, and "no user yet" is not an acceptable substitute.

## 6. Criteria and evidence ceiling

The six numbered criteria are taken verbatim from the roadmap row and are already implemented in the frozen pack; they are summarised here only so the plan is readable on its own.

1. **One task list.** Five cards, one business goal each, no operational steps, fixed order, handed one at a time, never all at once.
2. **Pass rule.** Every task is run; at least 4 of 5 are completed independently; throughout the session the developer gives no hint. P0 environment help (logging in, window size, input method) is allowed and logged; any P1–P4 — pointing the way, operating for the user, explaining a term, confirming an answer — fails that user, even one sentence.
3. **Control.** The same five tasks through the existing manual process. The AI path must be no worse on median total time and no worse on median error count, and strictly better on the pre-declared item, which is **error count**.
4. **Failures kept.** Every failure enters the ledger as it happened: operation path, sticking point, and the screen fact at that moment. Pass rates alone are not acceptable.
5. **Machine-checkable corroboration.** Task-list file, result table, and the audit or trace rows sharing one `conversationId` or trace id must line up task by task.
6. **Reverse proof.** Turn the AI path off — disable the tools through `PUT /ai/governance/policy`, or remove the assistant entry — and run only the manual process. If neither is possible, write "reverse proof not done"; never write it as done.

**Evidence ceiling.** E3 is the default: real stack, real data, real pages, but the same operator and the same machine. A real business user does **not** by itself raise the ceiling to E4 — E4 requires independent attestation from the client side, and the user must rule on it. Until that ruling exists, the report must not use E4 or the words "acceptance passed".

**One lesson from N5 is a hard rule here.** N5's zero-help record, screenshots and signed sheet were waived after the session, which left its fourth criterion unproven. For YD-43 the hint ledger is the core criterion: it must be kept live during the session, and no post-session waiver may replace it. If the ledger does not exist, the session cannot claim "zero hints".

## 1. 目标与口径

**目标。** 在一份已交付、已 pin 的产物上，让**一个真实交付项目**的真实业务用户，各自独立完成同一组五件事（每件一句业务目标），全程无开发者提示；并把 AI 路径与该项目**现有人工流程**按整场中位耗时、中位错误条数做对照。

**口径——自用交付。** KeelBase 不是拿到市场上卖的产品，而是我方承接企业交付项目所用的平台。因此被测对象是**某一个实际交付项目**的真实业务用户：不是随机第三方，不是按 recipe 复现的开发者，也不是受训过的复测者。评审原案写的是 3–5 人；按自用交付口径收窄为**该项目实际可用的业务用户数**，如实记录，不凑人。

**与既有条目的分工。** `YD-28` 量的是非作者开发者按 recipe 复现一次交付；`YD-36` M7 量的是一名读者看不看得懂页面；YD-43 量的是真实业务用户能不能在真实业务数据上**把活干完**，并与现有人工流程做效率对照。三条互不替代。

**预检（15 分钟，任一红即不开跑）。** 宿主 `/actuator/health` = 200；用户账号登录成功；助手对一句无害的话有回话；`audit_reader` 账号登录成功且 `GET /audit/logs?limit=1` 回 200；`GET /audit/verify` 回 200；本场对象在列表可见且与实例件一致；T2 那件待批项处于 `pending`；T5 那笔操作已存在且结局已知；T3 的区间与期望行数已定；录屏能跑且画面里看得出时间；本机时间与审计时刻同一时区。

**每场证据。** 每场一个新目录。录屏文件带字节数、sha256、时长、分辨率。每题至少一张终屏截图。导出文件带路径、字节数、sha256。相关审计行读数。任务清单文件（真正发出去的那份冻结题卡）、结果表、审计或轨迹 id 三者必须对得上：每题至少挂一个 id，三源一致。

**隐私。** 首选生产副本；用生产库须客户书面同意。脱敏范围写进实例件。录屏不上传、不公开。

**一条从 N5 带过来的提醒。** N5 跑在隔离栈上、材料是专门做的。若 YD-43 在客户环境跑，那套栈的做法不适用；能搬的只是预检纪律与证据布局，不是端口、种子数据和对象纸。

## 6. 判据与证据等级

六条判据照抄 roadmap 该行，冻结包里已经落地；这里只做摘要，让本方案能单独读。

1. **同一组任务清单。** 五张卡，每张一句业务目标，不含操作步骤；顺序固定，逐张发放，不许一次给全。
2. **通过标准。** 五题全部跑完；每名用户独立完成 ≥ 4/5；全程无开发者提示。P0 环境性协助（登录、窗口、输入法）允许并照记；P1–P4——指路、代操作、解释术语、确认答案——任一发生，该用户即判未通过，哪怕只有一句话。
3. **对照口径。** 同一组任务走现有人工流程。AI 路径须中位耗时**不劣**、中位错误条数**不劣**，且事先写明的**那一项更好**——那一项是**错误条数**。
4. **保留失败案例。** 每条失败原样入册：操作路径、卡点、当时屏幕事实。不许只报通过率。
5. **机器可核的旁证。** 任务清单文件、结果表、同一 `conversationId` 或 trace id 的审计/轨迹行，逐题对得上。
6. **反向可证。** 关掉 AI 路径——经 `PUT /ai/governance/policy` 逐工具禁用，或撤掉助手入口——只跑人工流程。两者都做不到就写「反向可证未做」，不得写成做了。

**证据等级。** 默认 E3：真栈、真数据、真页面，但同一操作者、同一台机器。**真实业务用户本身不自动把档位抬到 E4**——E4 要客户方独立出具证据，并由用户裁定。裁定之前，报告不得用 E4，也不得写「验收通过」。

**N5 的一条教训在这里是硬规则。** N5 的零求助记录、截图、签名件是场后裁定不补的，于是它的第四条判据无证。YD-43 的提示台账是核心判据，必须**场中同步记**，场后裁定不得替代；台账不存在，就不能宣称「零提示」。

## 7. 停止条件

| 触发 | 后果 |
|---|---|
| 到决策日仍无具名真实业务用户（见 §9） | YD-43 判**「未达成」**；不是「延期」，不是「待定」 |
| 实例件未填满或未冻结 | 不得开测 |
| 预检红 | 记「未测（环境）」；不记到用户头上 |
| 用户撤回同意，或离场超过 10 分钟 | 中止本场 |
| 有误操作他人数据的风险 | 冻结该屏、保留证据、停止 |
| 某个能力面缺失（例如没有第二人批准入口） | 该题记「未测（能力缺失）」；不删题、不把题目改软 |
| 客户不同意录屏或任何数据使用 | 不开测；若能改用有同意的副本，另行安排 |
| 开发者在场并作了解释 | 该场证据无效 |

## 8. 与 N5 的复用与不复用

**复用：**
- 审计读面的操作路径与机器读数方法：`audit_reader`、`/audit/verify`、导出列、BOM/CRLF 检查、`check-evidence.mjs`。
- 本机已验证的录屏设置：Game Bar、试录读数、地址栏可读。
- 预检清单的形状：health、登录、verify、对象可见、时钟与时区。
- 三者对账的字段口径：`conversationId`、trace id、execution id。
- N5 场次记录里的场次头与偏差栏版式。
- 隐私与脱敏规则。

**不复用：**
- N5 的判据。它的五条判据与六问逐格不是 YD-43 的判据；YD-43 是六条判据加对照组。
- N5 的任务单、答案键、对象纸与期望行数——它们绑死在种子栈的对象 #1 上。
- N5 的种子数据。种子库不是「真实业务数据」，不能拿来充数。
- N5 的读者。张杰（Alice）是具名非开发者读者，不是任何交付项目的业务用户，不得登记为 YD-43 的用户。
- N5 的场后裁补做法。缺截图、缺签名件、缺零求助记录在那里被裁定接受；YD-43 的提示台账是场中证据。
- N5 的通过裁定。「按用户裁定记为通过」是 N5 的事实，不是 YD-43 结论的先例。
