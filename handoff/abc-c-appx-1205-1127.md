## 2. The two readings of the 12-05 criterion / 12-05 判据的两种读法

**English**

The question is inherited from minute §十二 P0-E and packet D3. Neither reading has been ruled; D3 was still open on 2026-11-27.

**Reading A — "one `compile` success" (the minutes' literal wording)**

- **Observable evidence.** A `compile` workflow run exists whose job literally named `android-compile` has `conclusion: success`, plus the job's log. Run id, head sha and timestamps must be recorded.
- **What it proves when the guard is present.** Since `d939527`, the guarded script refuses exit 0 without a compile success marker, so a green `android-compile` should mean the CLI printed one of the markers. It also proves the CI path: label routing, checkout on the self-hosted runner, variable wiring.
- **What it does not prove.** That artifacts exist (M3), that the CLI actually executed rather than failed to start (M1 — a green still happens), or that the build is usable on a device.
- **Observable today?** **No.** No `android-compile` job can be dispatched while the runner is offline or the variable is unset; the last two visible runs show `skipped`.
- **The trap.** Taken literally, A was already satisfied by three 2026-11-22 runs (`44976731215`, `44976889790`, `44977295873`) — one of which was a **false green**. The 11-23 ruling draft exists precisely to stop that: it requires the run to be **within 14 days of the review, after the guard fix, with the run id kept**. If A is applied, state explicitly that the 11-22 runs are excluded, and say why (they predate both guard commits `cc8b1a3` and `d939527`, and one is a false green).

**Reading B — "one real HBuilderX compile"**

- **Observable evidence.** A dated compile log or artifact whose content could only come from a real HBuilderX run: the line `项目 KeelBase-App-X 编译成功。ready in <n>ms.` (real durations seen: 71,183 ms and 102,302 ms), and ideally a non-empty `unpackage/dist/build/app-android`. A bare job conclusion is not enough.
- **What it proves.** That the toolchain can actually build this project on that machine at that commit. It does not, by itself, prove the CI wiring — a manual VM log satisfies B without ever dispatching a job.
- **Observable today?** **No.** The VM has been frozen on the welcome screen for over a day (pixel-identical screenshots), the desktop never loaded, and no real compile has ever been run.
- **Since `d939527` A and B nearly coincide.** A CI `android-compile` success now requires a real marker, so the difference is mostly **where the evidence lives** (CI job vs VM log), not what it proves about compiling. A additionally proves the CI chain; B can be met without CI.

**How to write it when nothing is observable**

- Do **not** write "met", "success", "green", "gate usable", "acceptance passed", or "mobile works".
- Write instead: "Criterion [A/B] — **not met and not observable**: no `android-compile` job dispatched (variable absent, runner offline), no real compile log or artifact dated before 12-05. Readings: runner `<state>`, variable `<exists/absent>`, latest run `<id>` with `android-compile: <conclusion>`."
- Then state the consequence the 11-23 ruling attaches: if the criterion is not met on 12-05, App-X **freezes to documents**. Renewing instead is a new decision and must be written as one.
- Record which reading was applied. If the meeting has not ruled, write both readings and mark the item "needs a ruling on the day", not "passed".

**中文**

问题继承自纪要 §十二 P0-E 与 packet D3。两条读法都没有裁定；D3 在 2026-11-27 仍是开着的。

**读法 A —— 「一次 `compile` success」（纪要字面）**

- **可观察证据。** 存在一条 `compile` workflow run，其中名字就叫 `android-compile` 的作业 `conclusion: success`，外加该作业的日志。必须记下 run id、head sha 与时刻。
- **有守卫时它证明什么。** 自 `d939527` 起，被守卫的脚本在没有编译成功标记时不会以 0 退出，所以 `android-compile` 变绿应意味着 CLI 打出了某个标记。它还证明 CI 链路：标签路由、自托管 runner 上的检出、变量接线。

- **可观察证据。** 一份带日期的编译日志或产物，内容只可能来自真实 HBuilderX 运行：`项目 KeelBase-App-X 编译成功。ready in <n>ms.` 这一行（真实耗时见过 71,183 ms 与 102,302 ms），最好再有非空的 `unpackage/dist/build/app-android`。单看作业结论不够。

**观察不到时怎么写**

- **不要**写「达成」「success」「绿」「门可用」「验收通过」「移动端可用」。
- 这样写：「判据 [A/B] —— **未达成且不可观察**：无 `android-compile` 作业被派发（变量不存在、runner 离线），12-05 前没有真实编译日志或产物。读数：runner `<状态>`、变量 `<存在/不存在>`、最新 run `<id>` 的 `android-compile: <结论>`。」
- 然后写明 11-23 裁定挂的后果：12-05 未达成 ⇒ App-X **冻结到文档**。若改判续期，那是一个新决定，须作为决定来写。

## 4. False-green defences / 假绿防线

**English**

**What the two kinds of evidence actually are.**

- **Mock (what exists today).** `scripts/ci-compile.test.ps1` writes a fake `cli.cmd` into a temp directory and drives the guarded script with it. It proves the **judgement logic**: exit codes are passed through, a silent CLI fails, a marker passes. It proves nothing about HBuilderX, the toolchain, the project, or the machine.
- **Real compile (what does not exist).** An actual `cli.exe launch app-android --compile true` against this repository, producing `编译成功。ready in …` after roughly a minute and leaving build output. Only this proves the mobile side can be built at that commit.

**The historical false green, for calibration.** Run `44976731215` (2026-11-22) went **green in about two seconds**: the CLI printed `未检测到已打开的HBuilderX`, exited 0, and the job reported success. The two genuine runs that day took 71,183 ms and 102,302 ms. **Duration is therefore a cheap first filter** on any future "success".

**What the current guard closes, and what it leaves open.**

| Path | Status | Evidence |
|---|---|---|
| Silent CLI, exit 0, no compile | closed | marker requirement, `ci-compile.ps1:53-57` |
| Explicit "IDE not running", exit 0 | closed | `ci-compile.ps1:45-48` |
| Non-zero exit | closed | passed through, `:40-43` |
| **`cli.exe` exists but cannot execute** | **open — reproduces green** | today: guard returned exit 0 against a text file named `cli.exe`; `$LASTEXITCODE` is `$null`, `exit $null` exits 0 (`:40-42`). Independently recorded as M1 in `handoff/appx-guard-review-1127.md` |
| CLI hangs | never green, but ties up the runner | no `timeout-minutes` (M2) |
| CLI claims success, produces no artifact | **green — accepted risk** | guard reads words, not works (M3) |

**Rules for the review, so a mock is never taken as evidence.**

1. A green `compile-guard-self-test` job is **mock evidence only**. It says the guard's branches work; it says nothing about App-X compiling.
2. `android-compile: skipped` is **not evidence of anything**. It is the expected state of a closed gate.
3. `android-compile: success` counts only with (a) a run id and head sha, (b) a duration consistent with a compile (tens of seconds, not two), and (c) the log line carrying a success marker. If any of the three is missing, the reading is incomplete, not green.
4. A manual VM compile counts only with a dated log; it does not prove the CI path.
5. Never cite the 2026-11-22 runs as satisfying the criterion: one is a false green and all three predate the guard.
6. If the guard is quoted as "fail-closed", name the open hole (M1) in the same breath. "Closed on three paths, one hole left" is the accurate statement.

**中文**

**两种证据到底是什么。**

- **mock（今天有的）。** `scripts/ci-compile.test.ps1` 往临时目录写一个假 `cli.cmd`，用它驱动被守卫的脚本。它证明的是**判定逻辑**：退出码原样透传、静默 CLI 判红、带标记判绿。它对 HBuilderX、工具链、工程本身、机器一概不证明。
- **真实编译（今天没有的）。** 对这个仓真正跑一次 `cli.exe launch app-android --compile true`，约一分钟后打出 `编译成功。ready in …` 并留下构建产物。只有这个才能证明那个提交上的移动端能编出来。

**历史假绿，用来校准。** run `44976731215`（2026-11-22）**约两秒就判绿**：CLI 打印 `未检测到已打开的HBuilderX`、退出 0，作业报 success。当天两次真绿的耗时是 71,183 ms 与 102,302 ms。**所以「耗时」是任何未来「成功」最便宜的第一道筛子。**

**现行守卫封住了什么、漏了什么。**

| 通道 | 状态 | 证据 |
|---|---|---|
| 静默 CLI、退出 0、没编译 | 已封 | 成功标记要求，`ci-compile.ps1:53-57` |
| 显式「IDE 未开」、退出 0 | 已封 | `ci-compile.ps1:45-48` |
| 非零退出 | 已封 | 原样透传，`:40-43` |
| **`cli.exe` 存在但无法执行** | **仍开 —— 可复现为绿** | 今天对一个名为 `cli.exe` 的文本文件跑守卫，返回退出 0；`$LASTEXITCODE` 为 `$null`，`exit $null` 即退出 0（`:40-42`）。`handoff/appx-guard-review-1127.md` 独立记为 M1 |
| CLI 挂起 | 不会绿，但占住 runner | 无 `timeout-minutes`（M2） |
| CLI 自称成功、无产物 | **绿 —— 已接受风险** | 守卫信的是 CLI 的话，不是它的活（M3） |

**复核规则，确保不会把 mock 当证据。**

1. `compile-guard-self-test` 变绿**只是 mock 证据**。它说明守卫的分支有效，对 App-X 能不能编译不置一词。
2. `android-compile: skipped` **不是任何证据**。那是闸关闭时的应有状态。
3. `android-compile: success` 只有在同时具备三条时才作数：(a) run id 与 head sha；(b) 与编译相称的耗时（几十秒，不是两秒）；(c) 日志里出现成功标记。缺任何一条，就是读数不完整，不是绿。
4. 手工 VM 编译只凭带日期的日志作数；它不证明 CI 链路。
5. 绝不把 2026-11-22 那三次 run 当作满足判据：一次是假绿，三次都早于守卫。
6. 若引用「失败关闭」，同一句里必须点名未补的洞（M1）。准确的表述是「三条通道已封，仍余一个洞」。
