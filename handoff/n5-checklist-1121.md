## 2. 场次中（一条操作）

### 2.1 操作

1. A 在业务页发起一笔**真实业务写**（建议：修改一位客户的名称，走 CRM 客户页）。
2. 该写被闸扣下（方案 B 下是 `approval`），行动中心出现待批。
3. **B**（第二人）在行动中心批准；系统以 A 的身份执行。
4. 记下这次操作的 `executionId`：在行动中心/审计链展开行里，或从 `/audit/logs` 找同一时刻的三行。
   0.1.20 的批准行、试过行、执行行**共用同一个 `executionId`**。

> **待批 token 在哪个列表里（2026-11-21 彩排实测）**：`mode=approval` 的行**不会**出现在
> `GET /ai/my/confirmations`——该端点按设计只列 `mode=immediate` 的确认；发起人 A 读
> `GET /ai/confirmations` 队列得 403（仅管理员/审计读者可读）。要用接口自动取 token，须用
> **B（管理员）的令牌**读 `/ai/confirmations`。页面侧不受影响：B 在行动中心看得到待批，
> A 的助手面只说「需要批准」。见 §4 G9。

### 2.2 审计链页取三行

页面：`/keelbase-governance/audit-chain` → 「按业务对象 + 区间检索」。
类型选 `客户`，业务主键填客户 id，区间覆盖操作时刻，点「检索」。

期望：状态行写「扫描到的范围里命中 3 行」，表格三行分别是 **已执行 / 试过 / 已批准**。

> 失败表现：只命中 1–2 行 ⇒ 三行不齐；命中 4 行以上 ⇒ 区间里混进了同一对象的其它操作，收窄区间重来。
> 状态行写「这次检索没有完成」⇒ 读面故障，不是「没有这类行」。

### 2.3 六问逐格

逐行展开，读六格：

| 格 | 期望（这次操作） | 失败表现 |
|---|---|---|
| ① 谁 | `A 的姓名（账号 #A）`；批准行是 `B 的姓名（账号 #B）` | 裸 id、`未记录 —— 这一行没有记下调用方`、默认昵称冒充姓名 |
| ② 何时 | `YYYY-MM-DD HH:mm:ss UTC±HH:MM`，带偏移 | 不带偏移、与第二入口不同串 |
| ③ 哪个业务对象 | `客户 · #<id> · <掩码名> · 还在` | 出现 `crm_customer` 这类内部名；`未记录 —— 这次调用没有写下任何记录` |
| ④ 改成什么 | `改前: 客户名称 <掩码> …; 改后: 客户名称 <掩码> → <掩码> — 宿主现在的记录，不是写入那一刻的快照; 运行时没有记下的值，这里不替它补` | 把「宿主现在」写成「改后」；空白或只有 `—` |
| ⑤ 谁确认 | 执行行（方案 B，已定）：`A 确认了这次写（本人确认；客户端未记）`——已知措辞，见 §1.3 口径；批准行：`B 批准了这次写（这一行本身就是这次裁决；批准人见「谁」）`——**第五问以这一行为准** | `由第二人批准 —— 这一行没有记下批准人是谁`、`—` |
| ⑥ 结果 | 执行行 `已执行 · 真的执行了，写已经在系统里`；试过行 `试过 · 只记「试过」…`；批准行 `已批准 · 有人批准了，接下来会执行` | 整格只有一个枚举词（如 `executed`）、空白 |

> 判据是「逐格有答」且**任何一格出现「未记录 / 需解释」即未达成**。方案 B 的执行行第五格属于
> 「需解释」，所以 §1.3 那段口径**必须逐字写进场次记录**；写进去了就不是「没有解释」，而是「已解释的
> 已知措辞」。第五问的人以批准行为准。

### 2.4 两份导出

在同一个检索结果上点：

1. **「导出 CSV」** → `audit-six-YYYYMMDD-HHMMSS.csv`（六列业务 CSV）
2. **「导出核对 CSV」** → `audit-check-YYYYMMDD-HHMMSS.csv`（编号 + 六问 + 判定依据，八列）

期望：

- 两份都以 **UTF-8 BOM** 开头（Excel 打开中文不乱码）；
- 行尾 **CRLF**；
- 六列文件表头恰好 `谁,何时（带时区）,哪个业务对象,改成什么（改前 → 改后）,谁确认,结果`；
- 八列文件表头前可有一行 `# 相关、非硬链接：…` 的说明（元数据，不是数据行），表头八列；
- 数据行数 = 检索命中行数（这次是 3）；
- 任何一格带内部名（`crm_customer`、`update_crm_customer`、UUID、`executionId` 等）时，**整份拒绝导出**，
  错误只说「哪一问」，不回显那串名字。

> 页面无法直接构造内部名；这条负向由脚本与单测证明（`R7`）。

### 2.5 `/audit/verify`

页面：审计链页底部「链校验」区。也可直接 `GET /audit/verify`。

期望：`valid=true`、`brokenIndex=null`，并显示走过的节点数 `checked`。
失败表现：`valid=false` 且指出断在第几行；或端点 404/403（取不到，不是通过）。

### 2.6 第二入口

页面：`/keelbase-governance/action-center` → 找到这次写的台账行 → 展开 → 「宿主为这个对象记下的写」。

期望三处对上：

- **对象**：`对象：客户 · #<id>`，与六问第三格同一个类型词与主键；
- **时间**：`YYYY-MM-DD HH:mm:ss UTC±HH:MM`，与六问第二格**同一秒**；
- **谁**：姓名 + `#<id>`，与执行行的调用方同一个人。

> 这是**相关、不是硬链接**：两条轨之间没有共享编号；页面自己的提示与核对 CSV 的表头说明都这么写。
> 失败表现：宿主行没有记操作人（只显示破折号/空）、时间差一秒、对象是别的 id。

### 2.7 跑取数脚本

在仓库根目录：

```powershell
node scripts/n5-acceptance-reading.mjs --execution <executionId> --host http://127.0.0.1:48080 --token <bearer> --tenant 1 --csv D:\Rain6fish\handoff\n5-evidence-2026-11-2x\audit-six-<stamp>.csv --check-csv D:\Rain6fish\handoff\n5-evidence-2026-11-2x\audit-check-<stamp>.csv --sha256 D:\Rain6fish\handoff\n5-evidence-2026-11-2x --out D:\Rain6fish\handoff\n5-evidence-2026-11-2x\reading
```

期望：九行判据全部 `PASS`（`R5`/`R6`/`R8` 给了参数才有），`EXIT 0`。

> **`EXIT 2` 是「无法取数」，不是通过，也不是失败。** 宿主不可达、端点 404、快照缺一段、对象在扫描窗口
> 里找不到，都走这条。看到 2 就把原因抄进场次记录，不要判「验收失败」——但也**不能判通过**。

## 4. 已知缺口与口径（N5 前必须知道）

### G1 批准行的 `executionId`

- **0.1.20**：批准行、试过行、执行行共用同一 `executionId`（`GovernedExecutionEngine#performApproval`）。
- **更早的运行时**：批准行不带。脚本先按 `executionId` 直选；选不到已批准行时，按控制台同一条证据链
  （同工具、五秒内、恰好一行 `tool_confirmation/approved`）补上，并在报告里写明「按工具 + 五秒配上 #n」。
- 影响：按 `executionId` 选三行在 0.1.20 上是精确的；在旧版上要读那行说明，不能假装精确。

### G2 策略 `approval` 与第五问（**已裁定走 B**）

**2026-11-21 用户裁定：走 B**（宿主写 + 策略 `approval`）。执行行的「本人确认」作为已知口径逐字写进
场次记录（模板见 §3）；**第五问的「谁确认」以同一 `executionId` 的批准行为准**。下列技术事实不变：

- 运行时把 `authorization.riskStrategy` 取**工具声明的风险级**（`RiskLevel.strategy(tool.riskLevel())`），
  不是**生效的闸**。策略把 R3 工具改成 `approval` 后，`decision` 是「需第二人批准」，
  但线上仍写 `riskStrategy:"confirmation"`、`requiresConfirmation:true`。
- 控制台 `gateFromRow` 据此判 `confirm`，执行行第五问写「本人确认」；**实际是 B 批的**。
  批准行自己会写「这一行本身就是这次裁决」并点名 B。
- 只有声明为 **R4** 的工具才写 `human_approval`，第五问才会自动写「由第二人批准」。
  宿主今天**没有 R4 工具**；运行时示例 `escalate_customer` 是 R4，但对象 `follow_up` 没有宿主操作日志，
  所以方案 A 不采用。
- 脚本遇到这一形时产出一句 `方案 B 的已知口径` 的告诫（不改退出码）；场次记录直接抄那句话或 §1.3 的段落。

### G3 第二入口的宿主模块映射

- 本仓只有 `crm_customer → CRM 客户`（`governanceApi.ts` 的 `BUSINESS_LOG_TYPE`）。
- 其它对象（`follow_up`、`bpm_oa_leave`、`crm_contract`…）的第二入口**取不到数**，脚本报 `无法取数`，
  不报「对不上」。要覆盖更多对象，得在宿主侧补映射（另一个改动）。

### G4 时区

- 宿主操作日志的 `createTime` 是**本机钟面、不带偏移**；控制台与脚本都把它按本机时区渲染成
  `YYYY-MM-DD HH:mm:ss UTC±HH:MM`。
- 脚本与宿主不在同一时区时，第二入口的时间会误判（控制台也一样）。场次里让脚本与宿主跑在同一台机器。

### G5 审计读面最多 1000 行

- `/audit/logs` 的 `offset` 上限 1000，脚本最多扫 5×200。操作后**尽快**取数，不要隔天再找。

### G6 内部名拒绝无法在页面上构造

- 页面只渲染业务词，读者没法输入内部名去试。负向由 `R7`（脚本）与单测证明：
  注入 `crm_customer#1` 后，六列与八列都抛 `CsvLeak`，错误不回显那串名字。

### G7 默认昵称与掩码

- 演示库 `system_users.nickname` 默认是 `KeelBase`，所以「谁」可能显示 `KeelBase（账号 #1）`。
  这是**数据**不是代码；改它属于改宿主种子数据（N6 遗留，未动）。
- 记录名只留首字符（`修****`），这是控制台红线；场次记录不要再把原名抄回来。

### G8 五秒内同工具多笔

- 六问与批准人的配对规则是「同工具、五秒内、**恰好一条**」。同一工具五秒内两笔写/两次裁决时，
  第三问、第五问会如实说「未记录」而不是猜。验收操作一次一笔，避免连点。

### G9 待批行在哪个列表里（2026-11-21 彩排实测）

- **批准行不在 `/ai/my/confirmations`。** `ConfirmationStore.mine` 按设计只返回
  `mode=immediate` 的行（那是「等我本人确认」的列表）；`mode=approval` 的行等的是**别人**，
  由 `GET /ai/confirmations` 队列给出（分页，字段含 `token`、`arguments`、`status`）。
- **发起人读不到队列。** A 调 `/ai/confirmations` 得 403（队列只给管理员/审计读者）；
  这是按设计的收窄，不是故障。A 在自己的助手面只会读到「需要批准」的答复。
- **对验收的影响**：页面流程不受影响——B 在行动中心看到待批并批准即可，不需要 A 持有 token。
  只有想**用接口复现**时才要注意：取 token 的那一步要用 B 的管理员令牌；用 A 的令牌会得到
  空列表（my）或 403（队列），不要读成「没有待批」。
- 彩排读数：A 的 `/ai/my/confirmations` → `[]`；B 的 `/ai/confirmations?page=1&limit=10` →
  1 条 `mode=approval`、`status=pending`、`operator` 为 A。


目录递归、按名字排序，输出 `sha256  字节数  相对路径`。

### 5.5 退出码

| 码 | 含义 | 怎么读 |
|---|---|---|
| `0` | 取到数，全部判据通过 | 可以写「本次验收达成」 |
| `1` | 取到数，至少一条判据不通过 | 按行看是哪一条；不准写成「通过」 |
| `2` | **有一段取不到** | 不是失败，也不是通过；抄下原因，补数或改口径 |
| `64` | 用法错误 | 看 `--help` |

### 5.6 判据代号

| 代号 | 判据 |
|---|---|
| `R1` | 同一 executionId 下三行齐全（已执行/试过/已批准） |
| `R1b` | 批准人具名且是第二人 |
| `R2` | 三行六问逐格有答、无内部名 |
| `R3` | `/audit/verify` valid=true，且选中行都在链上、prev 相接 |
| `R4` | 第二入口对象/时间/谁三项对上 |
| `R5` | 六列 CSV 与屏幕同源（BOM/CRLF/列/行数/逐格） |
| `R6` | 八列核对 CSV（同上，另加说明行） |
| `R7` | 内部名拒绝（负向） |
| `R8` | 证据文件哈希（给了 `--sha256` 才有） |

> 方案 B 下，执行行第五格的「本人确认」**不会**让 `R2` 变红（它是 `answered=true`）；报告会在「告诫」
> 一节产出一句 `方案 B 的已知口径`，写明批准行点名了谁。场次记录照 §3 模板抄。
